[1] WORK : AI INVOICE AUTOMATION (CERBI)

Titan Aviation Fuels / Python, Claude API / in production

An invoice automation platform. It reads scanned and handwritten carrier invoices, works out what each one is, files the complete ones and organizes them into ERP import batches that a person checks, and puts the rest in front of a person with the reason it stopped.

[>] Try the invoice automation simulation (Cerbi) (interactive, fictional data)

THROUGHPUT
hundreds of documents a day
INPUT
scanned and handwritten, not just clean PDFs

-- ONE INVOICE, END TO END --

  1. 01 Ingest freight paperwork from email (shared mailboxes through Microsoft Graph), carrier and telematics APIs, and drop folders.
  2. 02 Identify who sent each invoice, using sender rules, known aliases and the ERP’s orders.
  3. 03 Extract the loads on every page: each document goes to Anthropic’s Claude API with one shared prompt plus what is known about that carrier, and comes back as structured JSON. Prompts are built for caching and documents are sent in batches to keep cost down.
  4. 04 Validate each invoice against the business rules, in order.
  5. 05 Review anything incomplete in a review inbox, with a short reason why it stopped.
  6. 06 File everything complete, and organize it into ERP import batches that a person checks before they go in.

-- DESIGN DECISIONS --

  • A person sees what the machine can’t decide. Nothing is guessed or silently dropped. An invoice that fails a check stops in a review inbox with a short, plain reason, so the fix is a decision, not an investigation.
  • Measure, then scale. Extraction cost and field coverage were measured on real documents before the full backlog was run, and every figure in the design is labelled as measured or estimated.
  • Built to be operated. Integrated with Microsoft Graph, the Samsara API and the company’s ERP; deployed on IIS with CI on GitHub Actions, so changes ship the same way every time.

[N] NEXUS : A FLARE BOARD FOR PEOPLE AND AI AGENTS

Sole developer / TypeScript, Cloudflare Workers / in use

A hub where tools, scheduled jobs and AI coding agents raise “flares” when something needs attention. Agents claim and diagnose them, and a person decides from a phone app. Around the flares it keeps a project board, an impact log and a living map of how the work gets done.

STACK
Hono, D1, R2, Durable Objects, Queues, Cron; a phone web app with push
SIZE
about 49,000 lines of TypeScript, about 1,000 automated tests

-- THE PROBLEM --

  • Too much work, in too many places. Projects arrive from other people faster than they finish, and where each one stands is spread across email, chat, repos and notes.
  • No clear answer to “what needs me?” Every tool’s alerts look equally urgent, so the one that matters gets lost.
  • AI agents need a supervisor. Agents can diagnose problems and open pull requests, but a person has to approve what they do, and not only from a desk.
  • Context and credit go missing. Picking a project back up means re-reading everything, and the impact of the work is hard to show later.

-- ONE FLARE, END TO END --

  1. 01 Raise a flare from any tool or agent. A repeat of the same problem updates the open flare instead of starting a new one.
  2. 02 Route it by severity: a push with sound, a silent push, or a line in the morning digest. Quiet hours hold everything but critical.
  3. 03 Claim it: an agent takes the flare on a short lease, adds its diagnosis and proposes a fix. If the agent stalls, the lease runs out and the flare reopens.
  4. 04 Ask the person anything the agent can’t decide. The flare moves to “needs me”.
  5. 05 Decide in Looking Glass, the phone app: approve, reject, reply, snooze or mute. Risky approvals need a fresh fingerprint or face check (passkey).
  6. 06 Ship an approved fix: a bot squash-merges the pull request only if its checks are green and the code hasn’t changed since the approval. Deploying is a second, separate approval.

-- WHAT ELSE IT HOLDS --

  • Workboard. Every project with who it is for, its finish line and a next action sized for one sitting. A pickup card lets a person or an agent resume where the last session stopped; agents draft handoffs and a person confirms them. A daily focus list and a weekly load check show when assigned work outgrows the hours.
  • Impact log. What changed in each area and by how much, drafted by agents and confirmed by a person, ready for reviews and write-ups.
  • Living map. A graph of teams, steps, paperwork and the systems behind them, readable by people and AI agents. It looks for gaps (an unowned step, a dead end, a manual hand-off between two systems, a long wait) and queues them as questions to review.
  • Claude connector. Claude apps read the board and draft notes, projects and map entries through an MCP server, signed in with OAuth and a passkey.

-- DESIGN DECISIONS --

  • Agents ask, people decide. Only a person can approve, snooze, silence or give an instruction, and an agent can never approve its own request. Every decision records whether it was confirmed with a passkey.
  • Noise control lives in one place. Tools report what they see; Nexus alone decides grouping, silences and how loudly to notify.
  • The phone only decides. Looking Glass holds no server or GitHub keys and never acts by itself; it sends decisions back and the board carries them out.
